# Технічне завдання для frontend: Barbershop

## 1. Загальна мета

Потрібно створити клієнтську частину навчального застосунку барбершопу. Застосунок повинен дозволяти відвідувачам переглядати послуги та працівників, реєструватися, бронювати вільний час і керувати власними записами. Адміністратор повинен мати окрему панель для керування користувачами, працівниками, послугами, записами та перегляду статистики.

Backend API доступний за префіксом:

```text
/api/v1
```

Інтерактивна документація API:

```text
/docs
```

## 2. Ролі користувачів

### Гість

Може:

- переглядати головну сторінку;
- переглядати список і деталі послуг;
- переглядати список і деталі працівників;
- фільтрувати працівників за послугою;
- переглядати availability;
- перейти до реєстрації або входу.

Не може створити запис до авторизації.

### Авторизований користувач (`user`)

Має всі можливості гостя, а також може:

- створювати власні записи;
- переглядати свої записи;
- переглядати деталі власного запису;
- редагувати власний профіль;
- виходити з облікового запису.

### Адміністратор (`admin`)

Може:

- переглядати dashboard;
- керувати користувачами;
- створювати, редагувати та видаляти працівників;
- створювати, редагувати та видаляти послуги;
- призначати послуги працівникам;
- переглядати, створювати, редагувати та видаляти записи;
- змінювати статуси записів;
- переглядати статистику доходу та популярності послуг.

Для кожної сторінки, яка завантажує дані, потрібно реалізувати:

- loading state;

- підтвердження перед видаленням даних.

Помилки валідації потрібно показувати біля відповідних полів. Серверну помилку — у формі або через toast/notification.

## 6. Авторизація

### 6.1. Реєстрація

URL: `/register`

Поля:

- ім’я;
- прізвище;
- email;
- телефон — необов’язковий;
- пароль;
- підтвердження пароля — перевіряється тільки на frontend.

Валідація:

- усі обов’язкові поля заповнені;
- email має коректний формат;
- пароль містить щонайменше 6 символів;
- паролі збігаються.

API:

```http
POST /auth/register
```

Після успішної реєстрації потрібно перенаправити користувача на сторінку входу або автоматично виконати login окремим запитом.

### 6.2. Вхід

URL: `/login`

Поля:

- email;
- пароль.

API:

```http
POST /auth/login
```

Backend повертає `accessToken` і встановлює HTTP-only cookie. Access token потрібно зберігати відповідно до обраної архітектури frontend і додавати до захищених запитів:

```text
Authorization: Bearer <accessToken>
```

Під час cookie-запитів HTTP-клієнт повинен використовувати `credentials: "include"` або `withCredentials: true`.

### 6.3. Відновлення сесії

Після перезавантаження застосунку потрібно:

1. Викликати `GET /auth/me` з наявним access token.
2. Якщо access token прострочений, викликати `POST /auth/refresh` із cookie.
3. Зберегти новий access token.
4. Повторити початковий запит.
5. Якщо refresh неуспішний — очистити локальну auth-сесію та перенаправити на login.

Для запобігання кільком одночасним refresh-запитам рекомендується використовувати один спільний refresh promise або interceptor HTTP-клієнта.

### 6.4. Вихід

API:

```http
POST /auth/logout
```

Після успішного запиту потрібно очистити access token та локальний стан користувача.

## 7. Бронювання

### 7.1. Сторінка створення запису

URL: `/booking`

Рекомендований покроковий flow:

```text
Послуга → Дата → Працівник → Вільний час → Підтвердження
```

#### Крок 1. Послуга

- показати активні послуги;
- користувач вибирає одну послугу;
- показати ціну та тривалість.

API:

```http
GET /services?isActive=true
```

#### Крок 2. Дата

- показати календар;
- не дозволяти вибирати минулу дату;
- дата передається у форматі `YYYY-MM-DD`.

#### Крок 3. Працівник

- показати лише активних працівників, які виконують вибрану послугу.

API:

```http
GET /employees?serviceId=:serviceId&isActive=true
```

#### Крок 4. Час

- після вибору послуги, дати та працівника завантажити availability;
- показати кнопки з вільними слотами;
- якщо слотів немає, показати відповідний empty state та запропонувати іншу дату або працівника.

API:

```http
GET /availability?employeeId=:employeeId&serviceId=:serviceId&date=YYYY-MM-DD
```

Backend повертає час у UTC. Перед створенням запису frontend повинен сформувати повний ISO datetime у UTC.

#### Крок 5. Підтвердження

Показати:

- послугу;
- працівника;
- дату та час;
- тривалість;
- ціну;
- поле коментаря;
- кнопку підтвердження.

API:

```http
POST /appointments
```

Приклад body:

```json
{
  "employeeId": "68d7b91e7255902c534a1111",
  "serviceId": "68d7b91e7255902c534a2222",
  "startAt": "2026-10-12T15:00:00.000Z",
  "comment": "First visit"
}
```

Frontend не повинен надсилати `endAt` або `price`: ці значення визначає backend.

Якщо сервер повернув `409`, вибраний час уже зайнятий. Потрібно повторно завантажити availability та попросити користувача вибрати інший слот.

Якщо гість натиснув `Записатися`, потрібно перенаправити його на login, зберігши вибрану послугу та URL повернення.

## 10. Пагінація, фільтри та URL

Параметри таблиць і списків потрібно синхронізувати з URL сторінки. Наприклад:

```text
/admin/appointments?page=2&perPage=20&status=confirmed&employeeId=...
```

Це дозволить:

- зберігати фільтри після перезавантаження;
- використовувати browser back/forward;
- ділитися посиланням на відфільтрований список.

Типова відповідь списку:

```json
{
  "page": 1,
  "perPage": 10,
  "totalPages": 3,
  "totalItems": 27,
  "hasNextPage": true,
  "hasPreviousPage": false,
  "appointments": []
}
```

Назва масиву залежить від ресурсу: `users`, `employees`, `services` або `appointments`.

Пошукові поля рекомендується відправляти з debounce 300–500 мс. При зміні фільтра або `perPage` потрібно повертати `page` до `1`.

## 11. Робота з датою і часом

- API приймає ISO datetime.
- Availability приймає дату `YYYY-MM-DD` і повертає `HH:mm` у UTC.
- Перед створенням запису frontend формує ISO datetime у UTC.
- Для відображення користувачу дату потрібно форматувати послідовно в одній обраній часовій зоні.
- У запиті не можна передавати `endAt`: його розраховує backend.
- Необхідно заборонити вибір минулих дат і слотів.

## 12. HTTP-клієнт та обробка помилок

Рекомендується створити один спільний API client із:

- базовим URL `/api/v1`;
- автоматичним додаванням Bearer token;
- `credentials: "include"`;
- централізованою обробкою `401` і refresh token;
- єдиним форматом обробки API-помилок;
- скасуванням застарілих пошукових запитів, якщо це підтримує бібліотека.

Очікувана поведінка за HTTP-кодами:

- `400` — показати помилки введення або бізнес-правила;
- `401` — спробувати refresh, потім перейти на login;
- `403` — показати відмову в доступі;
- `404` — показати сторінку `Not found`;
- `409` — показати конфлікт, наприклад зайнятий слот або наявний email;
- `500` — показати загальне повідомлення та кнопку повтору.

- `AppointmentCard` або `AppointmentTable`;
- `AvailabilitySlots`;
- form fields із відображенням помилок.

## 14. Адаптивність і доступність

- Інтерфейс повинен коректно працювати на mobile, tablet і desktop.
- Таблиці admin panel на малих екранах потрібно робити горизонтально прокручуваними або перетворювати на картки.
- Усі поля повинні мати `label`.
- Кнопки та інтерактивні елементи повинні бути доступними з клавіатури.
- Модальні вікна повинні утримувати focus і закриватися клавішею Escape.
- Для loading/error/success станів бажано використовувати доступні ARIA-повідомлення.
- Колір не повинен бути єдиним способом передавання статусу.

## 15. Мінімальні критерії готовності

Frontend вважається готовим, коли:

- реалізовані всі публічні, користувацькі й адміністративні сторінки з цього документа;
- працює register/login/logout/refresh flow;
- захищені маршрути недоступні без відповідної ролі;
- працює повний сценарій бронювання;
- списки підтримують серверні пагінацію, сортування та фільтри;
- admin може керувати основними сутностями та статусами записів;
- dashboard відображає дані API;
- усі форми мають клієнтську валідацію та обробляють серверні помилки;
- реалізовані loading, empty й error states;
- інтерфейс адаптивний і придатний для керування клавіатурою.

## 16. Не входить у поточний обсяг

Backend поки не надає функціонал для:

- відновлення або зміни пароля;
- завантаження файлів і фотографій — використовується `imageUrl`;
- оплати;
- відгуків;
- email/SMS-повідомлень;
- окремого робочого графіка кожного працівника;
- самостійного скасування запису користувачем;
- локалізації контенту через API.

Ці елементи не потрібно реалізовувати у frontend без окремого розширення backend API.
